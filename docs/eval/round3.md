# Crosswalk evaluation, round 3 (26 Oct 2026)

Written by hand from the runs listed below. The Day-2 report, [`../eval-report.md`](../eval-report.md), is generated by `agent/src/eval/run.ts` and is unchanged below its round-3 note. Every number here was measured in these runs. The data behind the tables is [`round3.json`](round3.json): run ids, timings, token counts, verdicts and gate decisions, with no SEC value and no model output. The runs themselves are not committed, because they hold SEC values.

## How the runs were made

- **Code:** `f60fdb0` for the thirteen runs of sections 1 and 2: the answer gate of `c5901df` plus the cache-time fix (section 4). The six runs of section 3 used `5562457`, which adds the opt-in `--opaque` path and leaves ordinary runs unchanged. Stack: local Zetaris 2.4.3.1, the gateway on loopback, Ollama 0.40.7 and one RTX 4070 Ti SUPER (16 GB).
- **One run at a time, one command per run:** `cmd /c "npm run ask -- ..."`. Each round used its own data directory, seeded from the main one (memory, World Model, DQ file, contract ledgers), so the main state was not written.
- **Checks around each run:** before each run, the driver checked the card: utilisation under 25%, and no model resident other than the two below. It waited 30 s once, before run 10, when utilisation read 26%. nvidia-smi sampled the card every 500 ms, and Ollama's `/api/ps` was read before the run, 60 s into it and after it.
- **Settings, interleaved:** think on, think off, no model, Q8_0, in three rounds, then the warm Q1 2024 question. The flags were `--cold --think on`, `--cold --think off`, `--cold --no-model`, and `--cold --think on` with `CW_MODEL=nemotron-3-nano:4b-q8_0`.
- **Models preloaded:** both quantisations were loaded at context 8192 before the first run (4.4 s and 10.4 s), so no run includes a first model load. The agent keeps a model resident for 30 minutes between calls.
- **"The same answer"** means every field of every row equals the Day-2 reference cold run `r20261025T1546471209`: utility, served states, declarations by incident type, revenue tag, both revenue values, the change, stations, both degree-day totals and their change. For the warm question, the reference is the Day-2 warm run `r20261025T155631f0a7`.
- **"Replies rejected"** counts every planner reply the host refused (schema, allowed step, menu ids), first attempts and repairs together. A call refused twice becomes a host fallback step.
- **Load:** the CPU load averaged 42.5% (median 40%, maximum 85%; 516 samples every 5 s, 01:52 to 02:44 SGT). No ffmpeg process ran during the ablation.
  - Free host RAM at the start of a run, as the agent logs it, ranged from 1,802 to 4,954 MiB. The agent unloads the model when free RAM falls below 2,048 MiB.
  - Run 4 overlapped a two-minute browser check of the provenance drawer (section 4).

**What the repeats say, plainly:**
- **No model is fastest.** The no-model runs reach the same answer and governed keys in 32% of the think-on median, with the smallest spread.
- **Think off is faster than think on, with no loss of keys.** Every think-off run was faster than every think-on run: 211.7 to 219.1 s against 268.4 to 317.9 s. It used a third fewer output tokens and got the same 3 of 6 model keys VERIFIED. It also had more replies rejected (14 to 17 against 8 to 16) and more host fallback steps (7 to 8 against 4 to 8).
  - So on this question the shipped think-on setting costs time and buys no keys.
  - That rests on three runs each, and the setting is not changed in this round.
- **Q8_0 is worse than Q4_K_M on both counts.** It generates about 101 against 136 tok/s, takes a median 347.8 s against 274.2 s, and got 1 of 5 model keys VERIFIED against 3 of 6.
- **The model unloads mid-run.** In every run with the model, the card memory fell by more than 2,000 MiB between two samples and came back, which means the model was unloaded and reloaded. Each drop was the model's size: 2,972 to 3,172 MiB at Q4_K_M and 3,484 to 4,341 MiB at Q8_0. How often:
  - 3, 3 and 4 times in the think-on runs, 2 in each think-off run, and 5, 6 and 4 in the Q8_0 runs.
  - The slowest think-on run, 317.9 s (`r20261026T02241541a4`), had 4 such drops and started with 1,802 MiB of free host RAM, under the guard's 2,048 MiB. The RAM guard is the likely cause; its events are not saved in the run file.
- **The Day-2 single runs:** 275.2 s (think on) and 88.4 s (no model) fall inside these ranges. 227.9 s (think off) is 8.8 s above this round's think-off range.

## 3. Opaque columns: does the model find keys the column names do not reveal?

**Setup** (code `5562457`):
- **The copies:** `zetaris/sql/11_cw_opaque_create.sql` copies the eight views the Q1 2025 question probes as `cw.opq_*` views, with every column renamed `c1`, `c2`, ... in its original order. The originals are untouched, and the table names keep the source's name after the `opq_` prefix.
  - Each copy has its source's rows (`11_cw_opaque_select.sql`): 43, 1,937, 116, 97, 51, 56, 133,039 and 1,005.
  - The list of copies is `zetaris/manifest-opaque.json`. The gateway reads it at start, so it was restarted once with the documented recipe.
- **What `ask --opaque` does:**
  - It probes the copies instead of the originals and adds no view from the search.
  - It runs cold with no memory context, because remembered keys name the original columns, and one opaque run's verified keys would otherwise hint the next.
  - No column name matches a key pattern, so every column that is not floating-point becomes a key candidate. That gives 38 menu columns, each with its distinct count and two sample values, the same for the model and the baseline.
- **Unchanged:** the planner prompt, which already describes keys by their values (a 10-digit CIK string, an integer CIK, a "US-XX" location, a two-letter state code).
- **How proposals are measured:** every proposal goes through the generic `match_rate` statement, because the named join-map statements read the original views.
- **Runs:** three cold runs with the model (think on, Q4_K_M) and three without, interleaved.

With nothing to measure, `keys_proposed` failed twice, and every later checklist step that needs keys failed with it; the run ended after 5 chunks with the template note.

**Result, plainly:**
- **Neither proposer found a key.** The model proposed eight pairs and all were REJECTED; the name-based baseline proposed none. The model found nothing the baseline missed that also measured as a key.
- **The answer was reached in none of the six runs.** In the three model runs the gate withheld it: it needs the FEMA FIPS, CIK and station keys VERIFIED, and their named statements read the original views. The three baseline runs stopped before the answer step.
- **Even a perfect proposer could not have reached the revenue column this way.** Through the generic statement, the padded CIK key measures 34 of 1,937 when the frames are counted, and 0 of 43 when the snapshot is counted (the transform cannot be put on the other side).
  - So the experiment also shows a limit of the generic statement: it transforms and counts the left side only.
  - The governed CIK key gets 42 of 43 because its named statement counts the snapshot and pads the frames side, across all three revenue tags.
- **Next steps it points to:** measure both orientations of a pair, let the gate accept a generic key that matches a governed one, and score the model against a value-based baseline.

## 4. The cache time in the provenance drawer

- **Before:** the drawers of the 25 Oct runs said "source cached at: not reported by the gateway". The gateway did report the time: per source object, the last `CACHE TABLE` in its SQL log since the Zetaris driver started.
  - Checked live on 26 Oct: `describe_object` on `cw.states` returned `{"cw.states": "2026-10-25T08:35:25+08:00"}`, and the seven other question-path views returned their times too.
  - The discovery tools dropped the time: the statement's provenance did not carry it, and the evidence record was written with `null`.
- **Fix:** `f60fdb0`, with a loop test that fails on the old code.
- **Live, in the runs of sections 1 and 2:** every statement over a cached view carries the time. In each run the only statements without one are the two live DQ statements, which read the semantic layer rather than a cached view: 54 of 56 to 58 of 60 statements per cold run, and 48 of 50 in the warm run.
- **Checked in a browser:** the drawer of a revenue cell reads "statement cache hit; source cached at 25 Oct 2026 08:32:10 SGT".
- **Not fixed:** the committed demo run in `docs/demo-run/` was saved before the fix and still says "not reported".
